# 普通 BF16 M192 与单行 Dispatch 前向优化

## 方案与范围

普通 BF16 前向统一采用 GMM1 M192 和 `dispatchRows=1`，保存模式
none、BF16、MXFP8、auto 共用同一计算分块。GMM2、反向、MGroup、UDMA
保留原配置，不增加按 BS 或单个专家数切换 M128/M192 的特例。

前向基线为 train `deefdc1b8ab587687f2f3217d217162b5ffd59ed`。
目前 train `f9ce981c8da37637ea89e924afc426269ef23464` 已合入 PR38；
这两个 train 提交之间没有前向 Kernel 修改，因此本表的原版前向仍与当前
train 一致。本 PR 不包含反向 mask 修复、诊断旁路、内部打点、group
轮换、额外 buffer 槽或权重 NZ 预打包。

## 分块、调度与就绪

- GMM1 L1：`128×256×256 → 192×256×256`；L0：
  `128×256×64 → 192×256×64`。A/B 两槽、L1.K=256、L0.K=64、
  unit flag 流水不变。增加 M 减少 M 方向 tile 数及重复发起的逻辑权重读取。
- 所有专家使用根据实际行数、N tile 数和 AIC 数选择宽度的 N 条带调度；
  尾块、UB 平面及 SwiGLU→GMM2 完成计数目标一起适配。
- 每卡专家数 **<8**，且预估 `BS×TopK/E >= 768`、实际首个非空专家
  至少 768 行时，首专家使用 Ready384，后续专家整专家就绪。
  实际首专家不足 768 行时，本次全部专家整专家就绪，计算仍为 M192。
- 一个 Ready384 主体对应两个 M192 tile；尾块按实际有效行数处理，
  不补 token。Ready 优先的生产者轮次重排只用于足够大且 384 对齐的分片。
- 普通前向 Dispatch 每次搬运 **1 行**，保留两个 UB 槽及原有搬运事件。
  搬运总字节数不变；完成 payload 和路由权重搬运后才发布 Ready。
  发布、轮询和完成计数的单位没有改为 DMA chunk 数。

`DEEPEP_BF16_M192_FORWARD` 仅由普通前向入口启用 M192、Ready384 和单行
Dispatch。Host、反向、MGroup、UDMA 不启用该入口宏，继续使用原配置。
缓存命中、物理流量和并发争用仍需区分；本次不宣称已证明慢 group 的硬件根因。

## Workspace、控制信息与 UB

GM workspace、Dispatch 输出、保存格式和公开接口不变，框架无需适配。
Ready 控制区仍按 `ceil(maxRecvTokens/256)` 预留，Ready384 使用的计数器
不会更多；每次调用清零完整控制区。单行 Dispatch 不改变计数器数量和偏移。

Dispatch UB 的每槽容量为 `AlignUp(dispatchRows×K, 32)` 个 BF16 元素。
K7168 时，原两行每槽 28 KiB、两个槽 56 KiB；单行每槽 14 KiB、合计
**28 KiB**。后续 UB 分配仍由 TPipe 和同一布局计算，不依赖硬编码槽偏移。
同步、前缀和、计数清零及 TopK 权重暂存大小不变。Host 继续按原两行
检查 UB 容量，是保守上界，不放宽已有 K/N/EP 容量限制。

GMM1 原始 Gate/Up UB 平面各为 `192×256×2=96 KiB`，合计 192 KiB。
MXFP8 按最多 64 行分成三个片段，复用前等待上一片段 MTE3 完成；量化与
三类 clipping mask 暂存为 45 KiB，峰值 **237 KiB**，低于 248 KiB UB。
GM data、scale、mask 的行宽和偏移不变。Dispatch UB 与 GMM1 UB 属于
不同阶段，不将两者相加判断容量。

路由系数绕过 DCache 读取，修复跨专家同一缓存行命中旧值的问题。
BF16 保存保留原始、限幅前的 Gate/Up；FP32 SwiGLU 和 BF16 加权顺序不变。

## 四版性能对照

Ascend950、EP8、BS4096、N8192、K7168、BF16 保存。相同 Host、测试脚本、
输入缓存、随机种子和依赖，仅替换 Kernel SO。CATLASS 固定
`abeb80893e45c917d8148de3249290b0a23741c8`，CANN 为 9.2.0；每次运行前
确认八卡空闲。Timer、诊断旁路及 group 轮换关闭，预热 10 次、运行 110 次，
取末尾 50 条 NPU Kernel 耗时的各 rank 中位数，再取八卡中位数。

也不宣称完全消除所有慢 group。

`test/megamoe_bf16_test/test_mega_moe_backward.py` 的 CPU 参考，容差不变。
正式反向测试脚本修正有限幅中间量的保存值参考：原始／反量化 Gate/Up
与限幅前参考比较；计算梯度的参考仍使用限幅后的值，梯度参考和容差未改。
修正仅影响 `--check-intermediates` 的 Gate/Up 检查，不改变算子、参数或
保存格式。该测试修正随本 PR 提交；反向 Kernel 修复仍由 PR38 提供。
修正前后 9 组保存模式／limit 的 CPU 对照确认其余中间量参考完全一致。
正式测试入口另补 BF16/MXFP8、limit=0/0.5 的四组八卡中间量与梯度检查。

未搭配 PR38 时，M192/2 和 M192/1 都复现 train 已有的有限幅 MXFP8
反向错误；搭配已合入 train 的 PR38 后都通过。因此该已知问题不属于本次
Dispatch 改动，也不把其修复归入本 PR。保存 ABI 相同，前向优化与反向修复
没有代码或合并顺序依赖。

Host 检查覆盖 1/2 行 Dispatch 的 EP、专家数、K 对齐、奇数分片和尾行
容量；同时覆盖旧 M128/Ready256、新 M192/Ready384、重复调用清零及
payload/weight 完成后发布。MXFP8 布局检查覆盖含 mask 的 237 KiB 上界。
普通前向独立编译通过；MGroup/UDMA 仍采用原配置，本次没有做性能修改。
合入前相关 CPU 单元测试共 77 项通过，覆盖数据缓存、卡序与全局 rank、
路由、调度和保存模式／mask 元数据。物理卡顺序测试同时覆盖排序和非排序
设备列表；元数据测试按现有接口显式传入 `retain_dispatch_output`。

固定 M192、同一 N 条带及保存方式，仅比较整专家就绪和放开至 E≤7 后
首专家 Ready384，其他条件与四版性能对照相同。九对运行八卡输出一致。

九组中八组耗时下降，一组增加 3.505 µs（0.032%）。多数差异很小，

TopK 或单个专家数定制的规则。

## 验证范围与复现

主要性能结论针对 EP8、BS4096、上述 K/N。此前 M192/2 的 BS2048 回归
通过，采用同一策略；本次新增单行 Dispatch 没有以旧 BS2048 数据宣称收益。
其他 EP/K/N 的性能需要集成后继续验证；Host 仍要求 K%256=0、N%512=0。

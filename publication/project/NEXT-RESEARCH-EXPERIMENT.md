# 下一项小实验：梯度交付是否在下一次反向来源同步处放大等待

## 从数据得到的问题

同样的 raw kernel / copies / quota，B1 与 B3 的主要 GEMM 累计计时接近，已采集的 dX/dp 结束屏障也接近。但两者完整 backward 的原 KERNEL 区间比约1.54。进一步读取原始固定槽与V3四阶段计时发现，差异集中在 AIC_INIT；源码明确说明，routed redispatch 中它包含等待 X/概率等源数据重建，并不只是初始化。

四阶段诊断中，B1/B3 的来源发布／表同步区间为589453885/136631814 cycles；实际 X/概率 pull 区间为132712318.5/132705517 cycles，几乎相同。每个数来自同rank每call区间并集的累计，再取八rank中位数；没有拼接跨rank时钟，不能把列简单相加。

可核对证据：`diagnostics/backward-redispatch-phases.json`、`backward-ready-phases.json`、`backward-gemm-phases.json`、`backward-sync-phases.json`。这些都是带打点的一轮诊断，不能直接换算成正式加速。

假设：梯度服务、不同rank的后续kernel进入时机和collective来源同步发生相互影响。尚未证明是硬件竞争、通信进展顺序、host提交偏斜中的哪一种；不能仅凭等待较长就认为它可被消除。

## 先做小干预，不直接堆联合算法

2026-11-16续查：raw-control同SO筛查已结束，legacy/preserve为4.469495/4.472070s，无收益信号。另一项更基础的候选是将 `EnableGradientPipe` 中 `GradientKey` 缓存为每expert一个值，再保持原稳定排序。384份真实原始计划的整数oracle顺序完全相同，源码副本元素测试次数中位减少3.65625倍；尚无新kernel或实测收益。优先对其做单变量控制和数值验收，它属于可向所有复制策略开放的公共执行优化。

先等待 raw-control 同SO legacy/preserve 的公平性修正筛查结束，冻结正确的公共路径。新干预另立 child clone，不修改现有运行。

| 控制 | 仅改变什么 | 排除的问题 |
|---|---|---|
| B1现状 | 原立即交付 | 参考 |
| B1＋Native进入前完成旧服务 | 发送次数、字节、计划不变；在下一次Native提交前完成已有flight | 检查异步服务与全rank kernel进入边界是否冲突；如果只是把等待移到host且step不降，则保留负结果 |
| group边界交付 | 同一个原始group的两个FFN wave反向都完成后归并 | 检查向自然执行边界合并是否比每wave交付、GA2窗口或更新末更合适 |

第一轮只用 MaxVio10/same、共同形状与一轮匹配短诊断。数值先过强制副本、空owner、W1/W2、checkpoint及三更新，再测无Timer完整更新。若有信号，补最强适用基线与独立重复；不能只胜过较慢的公共原型。

group身份必须来自原PlanTicket `(step,group,wave,1)`，不能将wave当layer。首次前向已经形成的group计划集合决定完成边界；重计算不重复登记，反向每份贡献一次。需要绑定ticket时放在公共执行接口，不以策略名猜路由，不看未来microbatch路由。容量不足仍采用确定性合法回收并记录原因。

## 什么才可能发展成新策略

如果只需要固定group累积，属于有用的执行器优化。固定step末归并已有REM，普通缓存复用已有Afore，梯度流水已有MegaFlux/PlaceMoE；这些不能分别作为创新。

后续候选才是：对当前已就绪任务，联合评估新增副本带来的完整梯度债务、下一次全rank计算进入边界，以及可用于交付的真实窗口，再决定任务组／配额／驻留／交付。新副本的梯度成本是固定参数平面，不按token数线性缩小。必须超过“强任务分组＋公共缓存＋固定group交付”的简单组合，并在独立路由验证。

若干预仅移动计时区间、不改善完整step，或收益完全来自避免公共原型的进展问题，则不将其包装为planner创新。先修公共底座，重新评估是否还有值得联合决策的冲突。

本文件是待验证实验方案；B1进入前完成服务、group交付、新联合策略目前均未实现或实测。自然训练分布和设备端在线控制仍是后续验收项。

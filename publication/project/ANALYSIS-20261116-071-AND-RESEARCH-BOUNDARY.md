# 0.71%意味着什么：已有实验、执行边界与研究取舍

本次为只读证据复核与文献分析。没有启动训练、profiling、数值测试、重放或新设备任务；没有修改已验收源码、SO和历史计时。长期研究目标仍暂停。

## 结论

目前没有经实验确认的新的联合planner收益，也没有已经成立的顶会论文idea。0.7108%是一个公共梯度交付依赖控制的单轮小信号，不能代表任务选择、复制、驻留与梯度交付联合规划的收益。

当前证据更支持以下判断：在现有W2、固定调用/资源边界和受控路由上，固定分组已经很强；大量搬运和发送字节被消除后，完整更新仍未改善。继续在当前Python生命周期服务上增加规则，缺少足够依据。

可以保留一个待证伪的问题：在共同内存预算内，是否应把同参数版本的专家执行及其未交付梯度作为跨microbatch的一段生命周期，联合决定任务组合、副本启用、直接累积和交付边界？只有证明任务互补与这种生命周期复用存在可重复的冲突，并超过REM式固定布局/累积及普通分组等强基线，才有论文贡献候选。目前没有这样的证明。

## 1. 0.71%的真实含义

本地证据：[局部报告](gradient-ready-20261116/REPORT.md)、[配对身份审计](gradient-ready-20261116/diagnostics/pair-identity-audit.json)。

| 同一SO、同一B3路径的局部配对 | 秒/完整更新 |
|---|---:|
| call_stream：flush时等待调用时的整个当前流 | 4.23805325 |
| bank_write：等待对应FP32 bank最后一次写入的Event | 4.20792863 |

差值30.12462ms，耗时减少0.7108127%，加速比1.007159。每方式只有一个独立新进程；进程内20个测量更新不是20个独立重复。不能据此确认稳定收益，也不能排除进程间波动。

这项修改收窄flush的就绪依赖，绑定参数版本、专家、来源、槽位代次和准确贡献列表；没有改变任务选择、copies/quota、GEMM、梯度计算、权重和梯度流量、交付次数、FP32格式、owner、八条目预算、raw dW生命周期、现有drain和确定的P2P顺序。因此它没有消除全部梯度服务，只可能减少其中被过宽依赖阻塞的部分。

旧host-only诊断中B3预热后finish主机封套约160.55ms。这段时间包含服务流依赖、同步及必要工作，既不是纯通信，也不是可直接省去的160ms。只有它对完整更新最晚完成路径的影响才形成收益。本次配对没有再采集finish诊断，不能把30ms进一步归因到某个具体设备阶段，也不能声称其余130ms已被定位。

简单的依赖示意是：两个本可重叠的工作A和G被错误串联时，局部完成时间可能为A+G；放宽依赖后最多变成max(A,G)。实际训练还有其他依赖与资源争用。这个表达用于解释“等待变短不等于整步同幅缩短”，不是本轮测量分解。

## 3. 方向卡在哪里

### 3.1 专家偏斜与整卡瓶颈不是一件事

E256/EP8下，每卡固定home有32个专家。旧same/MaxVio10诊断的update2、16次原始前向中，专家MaxVio中位约9.983，但home-rank MaxVio中位约0.248，最大约0.303。最忙卡的assignment约为平均的1.25倍，而不是11倍。

仅在线性计算、忽略额外成本的示意里，把1.25倍负载拉到1倍，可节省这段计算约20%。这不是完整更新20%的上界，更不是实际收益：MoE GEMM非线性、通信、框架、重计算和优化器等仍然存在。当前没有合格的完整稳态设备依赖闭环，不能给出它们各自的关键路径比例。证据：[实际home-rank负载](priority-cache-20261116/diagnostics/actual-home-rank-pressure.json)。该数字范围限于上述诊断，不推广到所有路由/更新。

### 3.2 动态调度的合法选择太窄

W2中选择很少。交替热点下，MaxUtil与固定分组选到相同组合；same/random中更复杂的跨层/单任务选择没有表现出额外优势。FIFO的最小runset在W2是单任务，不能仅以超过它证明智能选择有效。

更关键的是现有执行域：同层32home＋32replica，跨两层64home＋0replica。跨层组合没有副本槽是实现约束，不是策略主动判断无需复制。目前并未提供任务互补与复制都可自由选择的统一动作空间。

### 3.3 缓存优化的对象，与最初设想的常驻不同

B0→B1累计远端权重字节减少约88.4%，但完整更新差距很小。在一个已准确分类的诊断更新中，318次访问有270次命中，其中148次来自同组另一wave，92次来自同调用重计算/反向，只有30次来自不同microbatch任务组。总命中率不能代表真正的跨microbatch收益。

同版本缓存命中后仍将独立bank本地拷进现有计算槽，并发布新的epoch ready；不是该专家永久留在计算槽，由跨调用worker持续消费。旧三更新固定访问序列的120次miss里98次是该版本首次使用，22次重复miss。仅扩大容量，在这段固定序列上至多额外省528MiB，不能免去版本首次使用。预取可能隐藏首次使用等待，但没有相应实测证明。证据：[缓存上界](priority-cache-20261116/CACHE-OPPORTUNITY.md)。

### 3.4 延迟的是交付，不是整个梯度生产过程

共同底座中B1→B3累计梯度远端发送从130272MiB降为58224MiB，减少约55.3%；统计范围为八rank、全部25更新，包括预热。B3仍没有更快。

当前每调用仍由native产生新的dW输出，再转换/累积到公共FP32 bank，随后归主。延迟交付没有减少这些调用的Wgrad计算，也没有移除每次输出、bank加法、实际贡献者观察和owner发布路径。满容量时B3还会提前flush，不能当作REM的完整固定布局/步末累积实现。

代码证据：[新dW分配](gradient-ready-20261116/stack/source/native-balanced/csrc/ops/mega_moe_bf16.cpp#L899)、[桥接入口](gradient-ready-20261116/stack/source/native-balanced/ascend_deepep/fsdp2_bridge.py#L499)、[公共梯度服务](gradient-ready-20261116/stack/tools/lifetime_device.py#L171)。不能仅依据这些代码认定每项分别造成多少步时损失。

### 3.5 Planner还不能控制关键执行边界

执行池仍有串行保护。公共梯度路径保留drain、设备计数读回CPU、贡献者all_gather_object、FP32 bank累积、确定P2P顺序与接收buffer复用。bank-ready只改flush依赖，没有消除这些边界。

因此当前主要是在单调用执行器之外管理跨调用状态，还不是让MegaMoE直接消费跨microbatch的专家tile、共享计算槽和梯度累积生命周期。不能仅靠更多planner系数获得尚未开放的执行自由度；也不能反过来把全部负结果都归咎于Python，称算法必然有效。

### 3.6 关键路径与真实工作负载证据仍不完整

旧前三更新约200ms的B1入口差距在新预热后检查中消失：legacy/cached最大约1.87/1.94ms。因此旧预热期来源等待不能解释正式稳态分数。

目前缺少完整稳态设备完成依赖闭环，尚不能判定剩余差距由算力、HBM、通信、串行服务还是它们的组合主导。人工路由也不能证明自然训练中有足够的同专家重用与跨任务互补。证据：[主机边界诊断](host-boundary-20261116/REPORT.md)。

## 4. 与论文的边界

此次重新核对的是以下关键段落，不声称全面精读了所有相关工作。

| 工作 | 已有机制及对本方向的约束 |
|---|---|
| [EasyBalance §5.3](https://arxiv.org/html/2608.07964v1#S5.SS3) | 推理中的跨层任务选择已存在，并已经评估与EPLB组合；“时间调度＋复制”不能仅靠组合命名为创新 |
| [REM §3.2、B.3](https://arxiv.org/html/2609.32398v1) | 已有global-batch副本布局、microbatch分配、固定optimizer owner及更新后累积梯度归主；这些机制本身不是空白 |
| [Afore §5](https://arxiv.org/html/2610.03203v1) | 推理AFD中已有副本复用、保护槽位及按暴露迁移成本决定复制；只说迁移净收益或缓存不够 |
| [MegaFlux A.2](https://arxiv.org/html/2610.00671v1) | 已按owner的远端副本数惩罚归并成本，承认完整梯度大小不随token份额缩小；也已有核内梯度流水 |
| [PlaceMoE III-D](https://arxiv.org/html/2610.14798v1#S3.SS4) | 已联合布局/映射并重叠副本梯度同步，更新前等待尾部；“考虑拓扑/梯度/关键路径”不是充分的新贡献 |
| [Tessera §3.2](https://www.usenix.org/system/files/osdi26-hu-weifang.pdf) | 已有就绪可移动任务池、截止时间、内存约束及延迟Wgrad填补bubble；这些调度组件也已有先例 |

这些工作的场景和执行器不同，当前负结果不否定其论文结果。尤其不能把我们的B3当成REM复现后宣称REM无效。

## 5. 值得保留的具体问题，以及为何仍只是候选

候选问题是：**在有限计算槽和梯度bank预算下，任务互补与同专家生命周期复用何时冲突，是否需要联合决定一个专家执行实例的开启、复用和交付边界，才能缩短完整更新？**

同层/同专家任务聚在一起可能共享权重与梯度累积，减少中间梯度平面的重复物化、搬运和交付；这不自动减少Wgrad的数学计算量，等待它们也可能耽误其他依赖。跨层互补可以平衡当前卡负载，却可能激活更多不同权重和未交付梯度。多开副本可缩短某次调用，却增加完整梯度义务和owner尾部。三种选择的相互影响才是待证明的研究对象。

如机制成立，系统的调度单位应包含(version,layer,expert,execution-rank)的权重可用性、计算slot租约、已就绪任务tile、FP32累积及未交付贡献、owner与释放/交付边界。执行器需要在现有正确性约束内真正支持跨调用复用与直接累积；dx仍及时返回，参数/optimizer owner固定，不跨更新欠梯度，不读取未来尚未就绪的路由。

这不能包装成“改成原地累积就是论文”。REM等已经说明跨microbatch累积的合理性。可能的差异必须体现为：在有限预算、动态就绪和不同owner服务压力下，联合决策确实胜过固定global-batch布局、固定归并时机、普通缓存、固定分组/FIFO以及简单叠加；并说明哪个真实完成依赖改变了。

继续按顶会研究投入至少需要三条证据，目前均未具备：

1. 自然或独立训练路由中存在同时就绪的互补任务和足够的同版本复用，且不是人工安排出来的唯一特例。
2. 强基线下仍有稳定、可归因的暴露工作；联合决策能改变它，不是减少已经被隐藏的字节或只挪动等待位置。
3. 同资源、同执行器、同数值更新语义下，联合方法超过最强简单组合，并在不同路由上说明有效与失效条件。

如果固定分组、REM式布局/累积或普通执行器优化已经获得全部收益，就应收束这一planner论文题面。若主要问题只是重复扫描、同步过宽、元数据观察或buffer生命周期，应作为工程优化交付；已有约6%的公共优化属于这一类，仍是有效成果。

本次不启动上述验证。继续暂停设备任务，保留负结果、源码资格和归档；本报告不将条件性研究问题升格为已接受的新实施计划。
